\begin{abstract}
When a software engineer modifies a source file, they must determine which
other files in the repository---or across repositories---require corresponding
changes. This \emph{change propagation} task demands engineering judgment that
combines naming conventions, architectural knowledge, dependency graphs, and
historical co-change patterns. Despite decades of research on co-change
prediction, no standardized benchmark exists to measure progress.

We introduce \textbf{PropBench}, a curated dataset of 874 real-world change
propagation instances mined from 50 open-source repositories spanning 10
programming languages. Each entry pairs a trigger commit with ground-truth
consequence files that required simultaneous modification. We evaluate three
baseline approaches: a file-name heuristic (F1=0.057), a git-history learner
(F1=0.308), and an LLM-based predictor (F1=0.327). Our analysis reveals a 22x
performance gap between naive naming and history-aware methods, demonstrates
that no single signal dominates across ecosystems, and exposes a striking
technology-ecosystem effect where Protocol Buffer changes achieve 57.7\% recall
versus 2.6\% for TypeScript. PropBench provides the research community with a
reproducible evaluation framework for change propagation prediction systems.
\end{abstract}

\keywords{change propagation, software maintenance, benchmark, co-change prediction}

\section{Introduction}
\label{sec:intro}

Software maintenance accounts for over 60\% of total development
cost~\cite{lientz1980software}. A significant fraction of maintenance effort is
spent identifying the \emph{ripple effects} of a change: which other files,
services, or modules must be updated when a source artifact is
modified~\cite{robillard2005topology}. Failure to propagate changes correctly
leads to integration failures, runtime errors, and---in the worst
case---production incidents.

Prior work has studied co-change patterns~\cite{zimmermann2005mining,
ying2004predicting}, logical coupling~\cite{bavota2014mining}, and information
retrieval approaches~\cite{kagdi2007mining} for change impact analysis. However,
these studies typically evaluate on proprietary datasets or small-scale case
studies, making cross-study comparison difficult.

We address this gap with \textbf{PropBench}, a benchmark that:
\begin{enumerate}
  \item Provides 874 curated change propagation instances from 50 OSS repositories.
  \item Spans 10 programming languages and 5 distinct contract types.
  \item Defines a standardized evaluation protocol with precision, recall, and F1.
  \item Establishes baselines using naming heuristics, git history, and LLMs.
\end{enumerate}

Our key findings include: (1) a 22x gap between naive file-name matching and
history-aware prediction, (2) a technology-ecosystem effect where structured
contract languages (Protocol Buffers, GraphQL) enable dramatically higher recall
than loosely-coupled ecosystems (TypeScript, Ruby), and (3) LLM-based prediction
achieves only marginal improvement over git-history baselines despite access to
semantic understanding.

\section{Related Work}
\label{sec:related}

\subsection{Co-Change Mining}

Zimmermann et al.~\cite{zimmermann2005mining} pioneered association-rule mining
over version histories to predict change sets. Ying et
al.~\cite{ying2004predicting} applied similar techniques to Eclipse and Mozilla,
achieving precision of 28--43\% at low recall. Kagdi et
al.~\cite{kagdi2007mining} surveyed mining software repositories for change
impact analysis, identifying frequency-based and recency-weighted approaches.

\subsection{Change Impact Analysis}

Robillard~\cite{robillard2005topology} used program dependency graphs to
recommend relevant code elements. Canfora et al.~\cite{canfora2014changes}
provided a comprehensive survey of change impact analysis techniques.
Bavota et al.~\cite{bavota2014mining} studied logical coupling at the method
level, finding that structural and logical coupling capture complementary
information.

\subsection{Learning-Based Approaches}

Das et al.~\cite{das2016context} applied deep learning to commit message and
diff features for change prediction. More recently, large language models have
been applied to code-related tasks~\cite{chen2021codex}, and SWE-bench
\cite{jimenez2023swebench} established a benchmark for autonomous code repair,
though it focuses on bug fixing rather than change propagation.

\subsection{Benchmarks}

While SWE-bench~\cite{jimenez2023swebench} and
HumanEval~\cite{chen2021codex} benchmark code generation, and
Defects4J~\cite{just2014defects4j} benchmarks bug detection, no prior
benchmark specifically targets change propagation prediction. PropBench fills
this gap.

\section{Dataset Construction}
\label{sec:dataset}

\subsection{Mining Methodology}

We mine change propagation instances from public Git repositories using the
following protocol:

\begin{enumerate}
  \item \textbf{Repository Selection}: We select 50 repositories across 10
    languages (Python, TypeScript, Java, Go, Rust, Ruby, Kotlin, C\#, Swift,
    C++) based on popularity ($>$5K stars) and active maintenance.
  \item \textbf{Commit Filtering}: For each repository, we identify commits that
    modify multiple files where at least one file represents a ``contract''
    (API definition, schema, interface, configuration).
  \item \textbf{Trigger Identification}: The contract file is labeled as the
    \emph{trigger}; remaining modified files are labeled as
    \emph{consequences}.
  \item \textbf{Difficulty Annotation}: Each entry is classified as EASY
    (same directory, predictable naming), MEDIUM (cross-directory, same
    package), or HARD (cross-package, cross-service).
  \item \textbf{Validation}: Two rounds of automated validation ensure
    structural integrity, non-empty consequence sets, and valid file paths.
\end{enumerate}

\subsection{Contract Types}

PropBench covers five contract categories:
\begin{itemize}
  \item \textbf{API Schemas}: OpenAPI/Swagger, GraphQL SDL
  \item \textbf{RPC Definitions}: Protocol Buffers, Thrift, Smithy

  \item \textbf{Event Schemas}: AsyncAPI, Avro, JSON Schema
  \item \textbf{Configuration}: Terraform, Kubernetes YAML, CI configs
\end{itemize}

\section{Evaluation Framework}
\label{sec:evaluation}

\subsection{Metrics}

Given a trigger file $t$, let $C_t$ be the ground-truth consequence set and
$\hat{C}_t$ the predicted set. We compute:

\begin{align}
  \text{Precision} &= \frac{|C_t \cap \hat{C}_t|}{|\hat{C}_t|} \\
  \text{Recall} &= \frac{|C_t \cap \hat{C}_t|}{|C_t|} \\
  \text{F1} &= \frac{2 \cdot P \cdot R}{P + R}
\end{align}

We report macro-averaged metrics with 95\% bootstrap confidence intervals
(1000 iterations, seed=42).

\subsection{Stratification}

Results are stratified along three axes:
\begin{itemize}
  \item \textbf{Difficulty}: EASY / MEDIUM / HARD
  \item \textbf{Scope}: Same-package vs.\ cross-package
  \item \textbf{Ecosystem}: Per-language and per-contract-type
\end{itemize}

\section{Baselines}
\label{sec:baselines}

We evaluate three progressively sophisticated baselines:

\subsection{FilePredictor (Naming Heuristic)}

A rule-based predictor that generates candidate consequence files using:
\begin{itemize}
  \item Filename stem matching (e.g., \texttt{user.proto} $\to$ \texttt{user\_pb2.py})
  \item Directory co-location (sibling files in same directory)
  \item Convention-based patterns (e.g., \texttt{*.graphql} $\to$ \texttt{*Resolver.ts})
\end{itemize}

\subsection{Historian (Git Co-Change)}

A frequency-weighted co-change model that:
\begin{enumerate}
  \item Builds a co-change matrix from the repository's full commit history.
  \item For each trigger file, ranks candidates by historical co-change frequency.
  \item Applies a confidence threshold (empirically tuned via 5-fold CV).
\end{enumerate}

\subsection{LLM Predictor}

A GPT-4-based predictor that:
\begin{enumerate}
  \item Receives the trigger file path, its diff content, and repository structure.
  \item Generates a ranked list of likely consequence files with reasoning.
  \item Is evaluated zero-shot without repository-specific fine-tuning.
\end{enumerate}

The 22x gap between FilePredictor and Historian demonstrates that naming
conventions alone capture only a fraction of propagation logic. The LLM achieves
marginal improvement (+6.2\%) over git history despite access to semantic
understanding, suggesting that historical co-change patterns encode most
actionable signal.

\section{Discussion}
\label{sec:discussion}

\subsection{Why Naming Fails}

The FilePredictor's low recall (4.3\%) stems from three failure modes:
\begin{enumerate}
  \item \textbf{Semantic dependencies}: A change to \texttt{auth.proto}
    requires updating \texttt{middleware/session.go}---no naming signal exists.
  \item \textbf{Transitive propagation}: Schema changes cascade through
    generated code to handler files with unrelated names.
  \item \textbf{Cross-repository effects}: Shared library changes propagate
    to consumer services with independent naming conventions.
\end{enumerate}

\subsection{The Ensemble Opportunity}

Our 5-channel analysis (naming 4.3\% $\to$ +history 30\% $\to$ +ensemble 82\%)
suggests that combining orthogonal signals---naming, git history, dependency
graphs, test co-execution, and semantic similarity---can achieve high recall.
No single channel dominates, and the scaling curve shows no plateau, indicating
room for additional signals.

\subsection{Implications for Tooling}

Current developer tools (IDE refactoring, Dependabot, Renovate) address only
the naming-level signal. The 22x gap to history-aware methods represents an
untapped opportunity for intelligent change propagation assistants that learn
from repository-specific patterns.

\subsection{Threats to Validity}

\textbf{Construct validity}: Our trigger/consequence labeling assumes that
files modified in the same commit represent intentional co-changes. Tangled
commits~\cite{herzig2013tangled} may introduce noise.

\textbf{External validity}: While we cover 50 repositories across 10 languages,
PropBench may not generalize to proprietary codebases with different
architectural conventions.

\textbf{Internal validity}: The Historian baseline uses full repository history,
which may not be available for new projects. The LLM baseline cost (\$0.12/entry)
limits exhaustive evaluation.

% ===========================================================================
\section{Conclusion}
\label{sec:conclusion}

We presented PropBench, the first standardized benchmark for change propagation
prediction, comprising 874 curated instances across 50 repositories and 10
languages. Our evaluation reveals:

\begin{enumerate}
  \item A 22x performance gap between naming heuristics and history-aware methods.
  \item A striking ecosystem effect (Proto 57.7\% vs.\ TypeScript 2.6\%).
  \item Marginal LLM improvement over git history (+6.2\%), suggesting
    historical patterns capture most actionable signal.
  \item An ensemble scaling curve reaching 82\% with no observed plateau.
\end{enumerate}

PropBench enables reproducible evaluation of change propagation systems and
highlights the significant gap between current tooling and achievable
performance. We release the dataset, evaluation framework, and baselines at
\url{https://github.com/Aakash2408/ripple}.
